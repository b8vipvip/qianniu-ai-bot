# Knowledge Center V2 修订候选复核

本阶段建立在 `knowledge-feedback-v2.db` 的真实反馈闭环之上，目标不是让 Bot 自动改知识，而是把已经发生过的人工纠正整理成可审计、可复核的修订建议。

## 工作流

```text
Knowledge V2 本地直答
        ↓
买家明确负反馈 / Bot撤回
        ↓
人工客服给出不同答案
        ↓
feedback 记录 correction + manual_reply
        ↓
按 knowledge_id 收集最近 120 天纠正
        ↓
相似人工答案聚类
        ↓
检查不同买家数量 / 一致度 / 占比
        ↓
生成 pending 修订候选
        ↓
Knowledge Center → 修订
        ↓
人工查看当前答案 / 建议答案 / 原始纠正证据
        ├─ 应用所选 → 更新原知识
        └─ 驳回所选 → 仅关闭候选
```

## 证据规则

普通知识至少要求：

- 同一聚类至少 2 次人工纠正；
- 至少来自 2 个不同买家；
- 聚类平均相似度至少 0.74；
- 该聚类至少占当前知识可用人工纠正样本的一半；
- 建议答案与当前答案相似度低于 0.88，避免把纯措辞变化误判为知识错误。

高风险知识要求更严格：

- 至少 3 次人工纠正；
- 至少 3 个不同买家；
- 聚类平均相似度至少 0.82；
- 仍然必须人工确认，不存在自动应用路径。

## 为什么不用 AI 自动改写

修订候选直接采用真实人工客服纠正答案的聚类代表文本，不调用 AI 生成新事实。这样可以避免在价格、退款、账号、安全边界等高风险知识上发生“模型为了润色而新增事实”的问题。

后续如引入 AI，只应作为候选整理器，并继续以真实人工纠正为事实边界，不能绕过本阶段的人工批准门。

## 审计与防覆盖

修订候选保存在每店铺独立的：

`knowledge-revision-v2.db`

每条候选保存：

- 原知识 ID、标题和风险级别；
- 生成候选时的原答案；
- 建议答案；
- 真实人工纠正样本；
- 证据数、不同买家数、聚类可信度；
- pending / applied / rejected / stale 状态；
- 生成、处理和应用时间。

应用前会再次比较当前知识答案与候选生成时的原答案。如果中间已经有人手工改过知识，候选会自动标记为 `stale` 并拒绝覆盖。

## 与实时回复链路的关系

- 生成候选不会修改 Knowledge V2 Repository；
- pending 候选不会参与实时召回和直答；
- 只有人工点击“应用所选”后才调用 `KnowledgeEngineV2Repository.Save`；
- Repository 保存后继续走现有增量索引更新和旧知识镜像；
- 不改变现有 Confidence / Authority，只更新答案与 LastVerifiedAt；
- 原答案和纠正证据仍保留在 revision 数据库，便于事后追溯。

## UI

Knowledge Center 顶部新增 `修订` 按钮。

修订窗口包含：

- `分析并生成候选`
- `刷新`
- `应用所选`
- `驳回所选`
- 待复核 / 全部 / 已应用 / 已驳回 / 已过期筛选
- 当前答案与建议答案对比
- 每条真实人工纠正的买家和时间证据

系统明确保持 fail-closed：没有足够证据时不生成候选；没有人工确认时不改知识；原知识被改过时不覆盖。
