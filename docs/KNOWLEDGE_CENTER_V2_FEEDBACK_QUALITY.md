# Knowledge Center V2：真实反馈与知识质量闭环

最后更新：2026-08-25

## 目标

Knowledge Center V2 的第一阶段解决“本地知识如何快速、结构化、可解释地找到正确候选”。本阶段继续解决另一个问题：**真实客服使用结果如何反向影响后续知识选择，而不是长期依赖一个静态可靠度百分比。**

核心原则：

- Bot 本地知识真正发送成功，才计为一次知识命中；
- 买家明确正向确认或人工客服明确采用相同答案，才计为“已确认”；
- 买家明确否定后人工客服给出不同答案，计为“人工纠正”；
- Bot 回复发生撤回，计为“撤回”；
- 千牛输入框、发送按钮、会话确认等**传输发送失败只单独统计，不作为知识错误证据**；
- 沉默不等于正确，不因为买家没有继续追问就自动增加可靠度；
- 反馈只做小幅排序修正，不允许一次偶发反馈把权威业务知识突然降级或自动删除。

## 数据存储

知识事实继续保存在：

```text
knowledge-center-v2.db
```

真实使用反馈采用独立、追加式事件库：

```text
knowledge-feedback-v2.db
```

事件主要包含：

```text
sent
send_failed
accepted
buyer_negative
correction
withdrawal
```

每条事件关联 `KnowledgeId / Seller / Buyer / Question / Answer / Evidence / CreatedAt`。

使用单独事件库的原因是知识内容和运行证据属于不同生命周期。知识编辑不会覆盖历史反馈，反馈增长也不会修改知识正文。

## 反馈判定

### sent

只有 `SendTextWithRetryAsync` 返回成功后，才记录 `sent`。仅生成答案、发送前被人工接管、相关性门控抑制均不计命中。

### accepted

当前只接受明确证据：

- 买家短回复“好的 / 可以 / 谢谢 / 明白 / 收到 / OK / 解决了”等明确确认；
- Bot 发送完成一段时间后，人工客服再次采用高度相同答案。

Bot 自己刚发送后的卖家侧消息回显会被识别并忽略，不能误算成人工确认。

### correction

为了避免把人工客服处理“下一条新问题”错误统计成纠正，当前使用保守策略：

1. 买家先对刚才的 Bot 答案出现明确否定信号，例如“不对 / 不是 / 错了 / 不支持 / 答非所问”；
2. 随后人工客服在同一短时间窗口内给出与 Bot 答案明显不同的回复；
3. 才记为一次 `correction`。

### withdrawal

如果当前知识直答对应的 Bot 消息进入撤回链路，记录 `withdrawal`。撤回是比普通纠正更强的负面证据。

### send_failed

记录会话确认、UIA、输入框、发送按钮等发送失败，但不降低知识质量。这样可以避免“千牛发送故障”污染“这条知识是否正确”的判断。

## 多店铺与买家别名

反馈数据库继续按店铺隔离。反馈 Pending 关联买家时同时使用 `BuyerIdentityAliasService.AreEquivalent`，因此同一个买家的内部 nick 与展示名不同不会造成证据丢失。

## 热缓存与性能

反馈聚合结果常驻内存。新增事件会在写入 SQLite 后同步增量更新聚合缓存，而不是让下一条买家消息重新扫描整个反馈数据库。

知识排序阶段只读取缓存中的轻量质量修正值：

```text
base confidence
+ accepted positive adjustment
- correction penalty
- withdrawal penalty
```

调整值被限制在较小区间，避免反馈噪声压过权威知识本身。

## 知识质量页

Knowledge Center V2 顶部新增“质量”入口，展示：

- 命中次数；
- 已确认次数；
- 人工纠正次数；
- 撤回次数；
- 纠错率；
- 发送失败次数；
- 综合质量评分；
- 最近使用时间；
- 健康 / 观察 / 低质量 / 未使用状态；
- 最近反馈事件。

支持筛选“低质量、观察、健康、未使用、最近使用”。

本阶段**不会自动禁用低质量知识**。低质量仅用于提示和轻度排序修正，避免自动学习系统因为少量异常会话自行删除或关闭重要业务规则。

## 与旧可靠度数据的关系

现有 `UseCount / AcceptedCount / CorrectionCount / WithdrawCount / Confidence / Authority` 继续作为历史基线；V2 质量页会把历史计数与新的追加式反馈事件合并展示。

因此升级不需要清空原知识，也不会丢失以前已经积累的人工纠正信息。

## 后续建议

下一阶段可以在真实运行数据足够后增加：

- 低质量知识批量复核工作台；
- 同一 Subject + Predicate 的纠正聚类；
- 从高频人工纠正中生成候选修订版本；
- 按商品、Intent、Predicate 查看质量分布；
- 可回放“问题 → 命中知识 → Bot答案 → 买家反馈 → 人工修正”的完整证据链。
